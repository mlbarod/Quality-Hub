# 품질 포털 요구사항

## 목표

여러 경로에 흩어진 공정 품질 지표와 관리 Rule을 한곳에서 빠르게 조회하고 시각화한다. 구분·라인별 Q&A 게시판을 통해 사용자와 관리 담당자의 문의 및 답변을 체계적으로 관리한다.

## 사용자와 권한

- 역할: 마스터, 관리자, 일반유저
- 인증: 사내 SSO
- 접근 원칙: 사내 SSO 인증 후 수집한 유저 ID와 소속부서가 마스터 계정 또는 등록된 권한 규칙과 일치하는 사용자만 포털에 접근
- 1차 시범 운영 예외: `SSO_ENABLED=false`인 배포는 기존 사내 리버스 프록시의 사내망·허용 IP 제한과 역할 미리보기를 유지하며, 이 모드의 사용자 ID Header를 실제 인증·권한으로 간주하지 않음
- 기본 차단: 마스터, 관리자 또는 일반 권한으로 판정되지 않은 사용자는 인증에 성공해도 포털 화면에 접근할 수 없음
- 권한 관리: 마스터만 유저 ID 또는 소속부서를 기준으로 관리자·일반 권한 규칙을 추가·변경·삭제할 수 있으며, 관리자는 권한을 관리할 수 없음
- 마스터 보호: 마스터 계정은 관리자·일반 권한 규칙과 별도로 관리하고 마스터만 부여·회수할 수 있으며, 마스터가 1명뿐이면 해당 계정의 권한 회수를 비활성화
- 적용 방식: 항목별 값 전체가 같은 `직접 일치`와 특정 텍스트를 포함하는 `텍스트 포함` 방식을 지원
- 충돌 처리: 한 사용자가 관리자와 일반 규칙에 동시에 일치하면 더 높은 관리자 권한을 적용하며, 마스터 권한은 규칙과 별도로 유지
- 일반유저: 개별 사용자 목록 대신 접근을 허용하는 일반 권한 규칙을 권한 관리 화면에 표시
- 데이터, 문서, 검색 결과 및 게시판 열람 범위는 포털 권한을 기준으로 제한
- 관리 대상 콘텐츠: Report, Rule&SOP, 변승위 Category 등 포털에서 등록·수정·삭제하는 콘텐츠
- 삭제 원칙: Report와 Rule&SOP는 사용자의 최신 요구에 따라 각각 `report_reg`, `rulesop`에서 실제 삭제하고, Q&A 등 숨김 처리를 지원하는 콘텐츠는 실제 데이터를 지우지 않는 복구 가능한 숨김 처리로 수행하며 복구는 마스터만 가능
- 이력 조회: 콘텐츠·권한·Q&A 상태의 변경 이력은 마스터만 조회 가능

## 주요 기능

### 품질 대시보드

- Report와 Rule&SOP가 사용하는 MariaDB/MySQL 접속 환경변수를 함께 사용하고 `dashboard_report`의 `url` 컬럼 한 건을 Spotfire 대시보드 URL로 사용
- 대시보드 선택 시 데이터를 별도 가공하지 않고 Spotfire Web Player 원본 화면을 iframe에 직접 표시
- 포털에서 별도 조회 권한을 추가하지 않고 Spotfire의 화면 구성과 조회 권한을 그대로 유지
- 새로고침 시 `dashboard_report.url`을 다시 조회하고 같은 Spotfire 원본 화면을 다시 로드
- 테이블 또는 URL이 비어 있거나 DB 조회·URL 검증에 실패하면 원인을 구분해 안내하고 다시 시도 제공
- 대시보드 Spotfire 영역의 최대 폭은 Report 뷰어 1710px보다 약 10% 넓은 1881px로 제공하되 화면 폭을 넘지 않음
- Spotfire SSO, iframe 허용 정책과 운영 인증 방식은 연동 환경에서 검증

### 각종 Report 조회

- 품질 Hub의 Report를 업무 카테고리와 카드 형식으로 구성하고 검색·필터 제공
- 마스터와 관리자가 Rule&SOP와 같은 카드·팝업 흐름으로 Report를 등록하고, 선택한 Report 출력 화면 우측 상단에서 수정·삭제
- Report는 품질 Agent와 같은 MariaDB/MySQL 접속 환경변수를 사용하고 `report_reg`의 `category`, `report_name`, `description`, `report_url`을 각각 카테고리, 이름, 설명, Spotfire URL로 사용
- 신규 등록 시 화면에 표시하지 않는 `user_id`와 `reg_time`을 현재 사용자 ID와 DB 현재 시각으로 기록하며 별도의 사용 중지 상태는 두지 않음
- 신규 등록 카테고리는 현재 `report_reg.category` 값을 제안하되 20자 이내의 새 카테고리도 입력 가능
- Report 선택 시 데이터를 별도 가공하지 않고 Spotfire Web Player 원본 화면 표시
- 포털에서 Report별 공개 범위나 조회 권한을 추가로 설정하지 않고 Spotfire의 화면 구성과 조회 권한을 그대로 유지
- 수정 팝업은 신규 등록 팝업과 같은 필드를 사용하며 기존 값을 채워 표시하고, 삭제 확인 후에는 카드와 `report_reg` 행을 즉시 삭제
- `report_reg`에 고유키가 없으므로 목록 조회 시 서버가 화면에만 사용할 임시 식별자를 발급하고, 수정·삭제 시 조회 당시의 6개 컬럼을 NULL-safe 방식으로 모두 대조해 한 행만 변경. `user_id`와 `reg_time`은 브라우저에 노출하지 않음
- 완전히 같은 6개 컬럼 값을 가진 중복 행은 서로 구분할 수 없지만 수정·삭제는 한 번에 한 행으로 제한하며, 목록 조회 이후 다른 요청이 같은 행을 먼저 변경하면 새로고침을 안내
- Report 카드의 예시 시각화는 목록을 불러올 때 여러 차트 유형을 무작위 순서로 배정하고, 제공 유형 수 이내에서는 카드끼리 중복하지 않음
- Spotfire URL은 원본 화면에 직접 사용하며 SSO, iframe 허용 정책과 운영 인증 방식은 연동 환경에서 검증

### 품질 Agent

- 사내 자체 LLM 서비스를 API로 연결하여 GPT형 대화 기능 제공
- 기본 우측 대화 패널에서 사용하고 필요할 때 전체 작업 화면으로 확장
- RAG 검색, OpenWebUI의 `gpt-oss-120b` 답변 생성과 MariaDB/MySQL 대화 History를 Backend API로 연결하고 패널·전체 화면이 같은 conversation 상태를 공유
- 답변의 줄바꿈·강조·목록·표 양식은 안전하게 정제해 표시하고 내부 RAG 출처 정보는 사용자 화면에 노출하지 않음
- 질문 전송과 답변 표시 중에는 패널·전체 화면을 최신 메시지까지 자동 스크롤하되 사용자가 위로 이동하면 자동 추적을 중단
- SSO 활성화 시 서버가 검증한 세션의 user ID를 대화 소유권에 사용하고 브라우저 Header 값은 무시하며, SSO 비활성화 시에만 역할 미리보기의 user ID를 테스트 식별값으로 사용

### 통합 검색 및 Rule&SOP 조회

- 각종 Report 조회와 Rule&SOP의 검색 대상은 게시글 제목으로 제한
- Q&A의 검색 대상은 게시글 제목, 질문 본문과 숨김 처리되지 않은 답변·댓글 내용
- 검색어를 공백 단위의 단어로 나누고, 입력한 모든 단어를 검색 대상 내용에 포함한 게시글을 단어 위치와 순서에 관계없이 모두 표시
- 포털에 접근할 수 있는 마스터·관리자·일반유저 사이에는 통합 검색 결과 차등을 두지 않음
- 결과에 콘텐츠 종류, 제목과 각 App에서 제공하는 요약 정보를 표시
- 검색 결과는 별도 팝업에 표시하고 선택한 Report, Rule&SOP 또는 Q&A 콘텐츠로 이동
- Rule&SOP 앱은 변승위 Category분류와 Rule&SOP의 두 영역으로 구성
- 변승위 Category분류 박스를 클릭하면 최신 그림을 별도 조회 팝업으로 표시함. 팝업은 그림의 원본 비율과 크기를 우선하되 화면 폭보다 큰 경우에만 가로 스크롤이 생기지 않도록 축소함
- 마스터·관리자는 Category 박스 오른쪽의 `사진 교체` 버튼에서 PC에 복사한 PNG·JPEG·WebP 그림 한 장을 붙여넣어 화면 미리보기를 확인한 뒤 최신 자료로 교체함. 파일 형식과 원본 해상도를 그대로 저장하며 10MB 이하, 가로·세로 각각 20,000px 이하로 제한
- 변승위 Category 그림은 품질 Agent·Report·Rule&SOP와 같은 DB의 별도 `quality_hub_change_category` 테이블에 저장하고, `singleton_id = 1`인 최신 자료 한 건만 유지해 새 저장이 기존 그림을 교체함
- 테이블에는 그림명·MIME 형식·용량·가로/세로 크기·BLOB, 최종 변경 사용자와 시각만 저장하고 Excel 표 JSON·검색 텍스트·원본 Excel 컬럼은 두지 않음
- 그림 한 장이어도 App에서 교체한 내용을 여러 사용자와 서버 인스턴스가 공유하고 재배포 후에도 유지해야 하므로 영속 저장소가 필요함. 현재 읽기 전용 컨테이너와 별도 오브젝트 스토리지가 없는 운영 구조에서는 기존 DB의 singleton BLOB을 사용
- 모든 포털 사용자는 최신 Category 그림을 조회할 수 있고, 마스터와 관리자만 그림을 교체할 수 있음
- Rule&SOP는 실제 DB `rulesop`의 `main_category`, `sub_category`, `item`, `title`, `url`, `reg_user`, `reg_date`를 조회
- `main_category`, `sub_category`, `item`을 각각 대분류·중분류·소분류 필터와 카드 설명에 사용하고 `title`을 카드 제목으로 표시
- 문서 카드 선택 시 대분류·중분류·소분류와 원문 링크를 상세 팝업에 표시하고 조회 버튼으로 `url`을 새 창에서 열기
- `reg_user`, `reg_date`는 조회 정렬과 서버 내부 데이터에 사용하되 화면과 API 응답에는 노출하지 않음
- 마스터와 관리자는 Report 신규 등록 버튼과 같은 형식의 문서 추가 버튼에서 수정 팝업과 동일한 다섯 필드로 Rule&SOP를 등록하고, 상세 팝업에서 `main_category`, `sub_category`, `item`, `title`, `url`을 수정하거나 확인 후 `rulesop` 행을 실제 삭제함. 일반유저는 조회만 가능
- 신규 등록 시 화면에 표시하지 않는 `reg_user`와 `reg_date`를 현재 사용자 ID와 DB 현재 시각으로 기록
- `rulesop`에 고유키가 없으므로 목록 조회 때 사용자별 임시 식별자를 발급하고 수정·삭제 시 조회 당시 7개 컬럼을 NULL-safe 방식으로 모두 대조해 한 행만 처리
- Rule&SOP 카드의 MOCK 문구, 상세 팝업의 개정 이력과 수정 시 개정 내용 코멘트는 제공하지 않으며 숨김 대신 실제 삭제를 사용

### Q&A 게시판

- 구분·라인별 공개 게시판
- 홈 품질VOE 카드의 대기 배지는 조회한 게시글 중 숨김되지 않은 `답변 대기` 상태의 건수를 표시하고, 게시판 데이터 갱신 시 함께 갱신. 조회 전에는 `확인 중`, 실패 시에는 `확인 불가`를 표시하며 0건도 실제 값으로 표시
- 모든 역할의 사용자가 질문과 답변·댓글을 작성
- 질문 작성 시 `Rule`, `SPC`, `FDC`, `TTTM`, `Report`, `WF Loss` 중 구분을 선택하고, 저장소에 포함하지 않는 환경변수 파일에서 불러온 라인을 선택
- 질문 목록에 등록일, 구분과 라인을 각각의 컬럼으로 표시하고 구분·라인 필터를 서로 겹쳐 열리지 않는 드롭다운으로 제공
- 질문·답변 작성 및 수정 편집기는 글씨 크기(pt)를 선택하며 기본 크기는 11pt. 선택한 부분 또는 이후 입력에 적용하고 저장·재편집·메일에서도 유지
- 추가 답변·댓글은 기존 대화 영역에서 `답변 작성`을 선택하면 펼쳐지는 리치 텍스트 편집기로 작성하고, 수정할 때도 같은 편집기를 사용
- 마스터와 관리자는 모든 질문의 처리 상태를 변경하고 최종 답변을 지정
- 마스터는 모든 질문과 답변·댓글을 수정·삭제할 수 있으며, 관리자와 일반유저는 본인 작성분만 수정·삭제
- 답변이 등록된 질문은 작성자가 수정할 수 있지만 삭제할 수 없으며, 마스터만 삭제 가능
- 처리 상태는 `답변 대기`, `답변 중`, `답변 완료` 사이에서 이전 상태로 되돌릴 수 있음
- 삭제는 복구 가능한 숨김 처리로 수행
- 포털 내부 알림 제공
- 목록·통합 검색은 질문·답변 평문을 조회하고, 이미지 포함 HTML은 해당 질문 상세 진입 시 조회. 동일 사용자·역할의 동시 목록 요청은 공유하고 15초 이내 조회 결과를 재사용
- 질문·추가 답변은 저장 성공 응답의 정제된 내용을 즉시 반영하며 전체 목록 재조회를 기다리지 않음. 등록 중 회전 표시와 중복 제출 방지를 제공. 조회·응답 계약과 실측 제한은 [Q&A DB 명세](QNA_DATABASE_SCHEMA.md)의 지연 개선 절을 따름
- 이미지가 포함된 질문·답변 본문은 UTF-8 기준 15MiB, JSON 전송 요청은 20MiB까지 허용. 클라이언트와 서버 모두 한도를 검사하며 원본 이미지를 임의 압축하지 않음
- 등록·저장 실패와 필수 입력 누락은 작성창 위 `저장 안내` 팝업으로 사유와 다음 행동을 안내하고 입력 내용을 유지. 용량 초과·로그인 만료·권한 부족·연결 문제·서버 장애를 일반 사용자 문구로 구분하며 HTTP 코드·SQL·내부 오류 메시지는 표시하지 않음. 응답 유실로 저장 여부가 불확실하면 중복 등록 전 목록 확인을 안내

### Q&A 외부 메일 알림 (2026-09-11 사용자 구현 승인)

- 메일 발송 API는 `POST https://openapi.samsung.net/mail/api/v2.0/mails/send?userId={작성자_Knox_ID}`이며, `userId`와 발신자는 현재 질문·추가 답변 작성자의 동일한 ID로 자동 구성. 기존 `KNOX_MAIL_USER_ID`는 무시하며 필수 설정에서 제외 (2026-09-12 작성자별 미발송 수정)
- 요청 헤더는 `accept: */*`, `Content-Type: application/json`, `Authorization: Bearer {token}`, `System-ID: {System id}`를 사용. 토큰과 System ID는 서버 환경변수로 제공하며, 사용자 확인상 토큰은 만료되지 않음
- 요청 본문은 `subject`, `docSecuType: PERSONAL`, `contents`, `contentType: HTML`, `sender: {emailAddress}`, `recipients: [{emailAddress, recipientType: TO}]` 구조를 사용. `sender.emailAddress`는 질문 또는 추가 답변 작성자의 `{knox_id}@samsung.com`으로 구성하고, 수신자 주소는 각 수신자의 `{knox_id}@samsung.com`으로 구성. URL의 `userId`와 본문의 발신자 ID를 일치시킴
- 신규 질문 메일은 권한 관리 탭에 등록된 관리자와 마스터에게 발송. 추가 답변 메일은 같은 관리자·마스터와 해당 질문의 원작성자에게 발송하며 원작성자가 일반 권한이어도 포함. 다른 일반유저 전체나 다른 게시글 작성자는 추가하지 않음. 주소 정규화 후 중복을 제거하며 본인도 수신 대상에서 제외하지 않음. 사용자 확인상 수신자 수 제한은 없음
- 메일 제목은 게시글 신규 등록 시 `[품질 Hub VOE] 게시글 등록:{질문 제목}`, 추가 답변 등록 시 `[품질 Hub VOE] 추가 답변: {질문 제목}`으로 구성
- 메일 본문은 사용자가 승인한 예시처럼 작성자·구분·라인, 게시글 바로가기 링크, 실제 질문 본문 순서로 표시. 2026-09-11 사용자 요청으로 `contentType: HTML` 본문에 VOE의 문단·강조·목록·인용·링크·표 서식을 유지하고 이미지는 `[이미지: 게시글에서 확인]` 안내로 대체. 임의 HTML 속성·외부 리소스는 제외하며 실제 Knox HTML 지원과 수신 표시는 미검증
- 설명용 성공 응답(`200 OK`, `success`, `messageId`)과 실패 응답(`401 Unauthorized`, `code`, `message`) 예시는 실제 Knox API 규격으로 확정하지 않음
- 발송 실패 시 추가 재시도는 최대 1회. 게시글·답변 저장 성공 후 비동기 발송하며 메일 실패로 저장을 취소하지 않고 실패를 기록
- 성공·실패 응답 구조와 성공 판정 기준은 미수령. HTTP 2xx는 접수·응답 검증 대기로 기록하고, HTTP 오류·네트워크 오류·시간 초과에 추가 1회 재시도. 실제 응답 본문에 따른 업무 오류 판정은 사내 검증 후 보완
- 추가 답변 메일에는 질문 원문 아래에 굵은 구분선과 `추가 답변` 제목을 넣어 새 답변 본문을 명확히 구분. 게시글 링크는 숫자 질문 ID로 상세 화면을 열도록 구성
- 설정과 구현 제한사항은 [품질VOE Knox 메일 알림](QNA_MAIL_INTEGRATION.md)을 따름. 실제 사내망 발송·수신 검증은 사용자가 직접 수행하며 아직 미검증

### 방문자 클릭 이력 (2026-09-18 사용자 구현 승인)

- 기존 DB의 `clicked_history`에 App 진입 시 `contents = NULL`인 행을 저장한다. 첫 콘텐츠 클릭은 그 진입 행의 제목과 클릭 시각을 갱신하고, 두 번째 콘텐츠 클릭부터는 제목을 담은 새 행을 추가한다. 콘텐츠를 선택하지 않고 나가면 NULL 행이 유지된다. 동일 콘텐츠를 다시 클릭하면 새 행을 남긴다.
- `category VARCHAR(20) NOT NULL`에는 `각종 Report조회`, `Rule&SOP`, `품질 VOE`, `통합 검색`, `품질 Agent` 중 하나를 저장한다. 메인 App 및 같은 App을 여는 내비게이션 버튼을 대상으로 하며 대시보드·권한 관리·화면 자동 복원은 기록하지 않는다.
- `contents VARCHAR(100) NULL`에는 Report 제목, Rule&SOP 문서 제목, 품질VOE 게시글 제목 또는 통합 검색에서 선택한 콘텐츠 제목을 저장한다. 변승위 Category분류 클릭은 정확히 `변승위 category 분류`로 저장한다. 품질 Agent는 항상 NULL이며 대화 내용은 수집하지 않는다.
- 통합 검색 결과 선택은 `통합 검색`으로 한 번만 기록하고, 자동으로 열린 목적지 App의 진입·콘텐츠 클릭으로 중복 기록하지 않는다. 목적지에서 사용자가 다시 클릭하면 해당 App의 새 클릭으로 기록한다. 품질VOE 목록 및 알림에서 게시글을 선택한 경우 게시글 제목을 저장하며 검색·바로가기 자동 진입이나 신규 글 저장은 게시글 클릭으로 기록하지 않는다.
- 100자를 넘는 제목은 유니코드 문자 기준 앞 100자를 저장한다. 제목을 저장할 수 없는 경우 NULL로 처리한다. `knox_id VARCHAR(20) NOT NULL`에는 SSO 활성화 시 서버가 검증한 사용자 ID를 저장하며 요청 본문·헤더로 다른 사용자 ID를 지정할 수 없다. SSO 비활성화 개발 모드에서는 기존 역할 미리보기 사용자 ID를 사용하므로 실제 방문자 식별 검증과 구분한다. ID는 자르지 않으며 없거나 20자를 넘으면 기록하지 않는다.
- `update_date DATETIME NOT NULL`에는 품질VOE와 동일하게 `UTC_TIMESTAMP() + INTERVAL 9 HOUR`로 계산한 한국시간을 저장한다. 진입 시각 조회·첫 콘텐츠 UPDATE·후속 INSERT에 같은 기준을 적용하며, 진입 응답 `entryDate`도 한국시간이다. DB 세션·컨테이너·조회 도구의 시간대에 의존하지 않고 초 단위 형식을 유지한다. 클라이언트가 보낸 날짜를 현재 시각으로 사용하지 않는다.
- 2026-09-18 사용자 승인으로 최초 `TIMESTAMP` 계약을 `DATETIME`으로 변경했다. [전환 DDL](../db/migrations/003_clicked_history_kst_datetime.sql)을 수동 적용하며, 적용 순서는 클릭 수집 중단 → 사용자가 기존 클릭 이력 삭제 → DDL 실행 → 변경된 서버 코드 배포·재시작이다. 기존 이력 삭제는 사용자가 수행하므로 삭제·이관·시각 보정 SQL은 제공하거나 자동 실행하지 않는다. 컬럼이 TIMESTAMP인 상태에서 새 저장 로직을 먼저 적용하지 않는다. DATETIME은 조회 시 시간대를 자동 변환하지 않으므로 HeidiSQL의 시간대 설정 변경은 필요하지 않다.
- `POST /api/clicked-history`는 `{ category, contents, entryDate? }`를 받는다. 진입 INSERT 성공 후 201과 DB 진입 시각 `entryDate`를 반환하고, 첫 콘텐츠 요청은 그 시각을 보내 사용자 ID·App·시각이 일치하는 NULL 행 한 건만 UPDATE한다. 이후 클릭은 `entryDate` 없이 INSERT하며 콘텐츠 저장 성공 후 204를 반환한다. NULL 행이 없으면 제목을 새 행에 저장한다. 이력 조회·삭제 API와 테이블 자동 생성은 제공하지 않으며 기존 테이블을 사용한다.
- 클라이언트는 진입 요청 응답 전 콘텐츠를 클릭해도 백그라운드에서 응답을 기다린 뒤 첫 행을 갱신한다. 홈 이동·App 재진입은 이전 진입 행과 분리하며 통합 검색 선택은 목적지의 이전 진입 행을 재사용하지 않는다. 주어진 스키마에는 고유키가 없고 DATETIME은 초 단위이므로 동일 사용자·App이 같은 초에 여러 탭에서 진입한 NULL 행들은 서로 구분되지 않는다. 조건에 맞는 한 행만 갱신하며 사용자별 저장 행 수와 제목은 유지한다.
- 클라이언트는 별도 비동기 요청으로 전송하며 화면·알림·로딩 표시를 추가하지 않는다. 저장 오류와 인증 만료는 원래 화면 동작을 막거나 로그인 이동을 유발하지 않는다. DB 연결과 대기열은 별도로 제한하며 오류는 서버에 기록한다.
- 요청은 `keepalive`로 화면 이탈 중 전송을 보완하지만 오프라인·브라우저 강제 종료·DB 장애 시 유실될 수 있다. 주어진 스키마에 이벤트 고유키가 없으므로 중복 저장 위험이 있는 자동 재전송·영속 재시도 큐는 사용하지 않는다. 진입 저장 성공 응답이 유실되면 NULL 행을 특정하지 못해 첫 콘텐츠가 별도 행으로 남을 수 있다. 운영 DB의 INSERT·UPDATE 권한·실제 SSO ID·저장 시각은 사내 환경에서 별도 확인한다.

1차 시범 운영은 기존 사내 리버스 프록시 뒤의 Docker Compose 단일 앱으로 배포한다. `.env.db`, `.env.rag`, `.env.gpt-oss`, `.env.sso`, `prototype/.env.local`은 환경 소유자가 별도로 관리하는 필수 환경파일이며 Git에 저장하지 않는다. 개발·빌드·배포 작업은 이 파일의 내용을 생성·수정·덮어쓰지 않고 승인된 원본을 그대로 사용한다. 미완료 단계는 운영 중 순차 진행하되 완료되지 않은 인증·데이터·검증 범위를 운영 완료로 표현하지 않는다.

## 현재 구현 경계

- 단계별 현재 상태와 판정의 단일 기준은 [개발 계획](DEVELOPMENT_PLAN.md)이며, 이 요구사항 문서에는 변동하는 단계 판정을 중복 기록하지 않음
- Q&A 질문·답변·태그·알림·변경 이력은 `quality_hub_qna_*` 5개 테이블을 사용하는 Backend API에 연결하며 브라우저 로컬 저장소를 운영 데이터 저장소로 사용하지 않음
- 통합 검색은 현재 DB에서 조회한 Report·Rule&SOP 제목과 Q&A 제목·본문·숨김 처리되지 않은 답변·댓글을 동적으로 반영
- SSO 활성화 시 서버 세션의 사용자 ID·표시 이름·역할로 Q&A API 권한을 집행하고 브라우저가 보낸 사용자 Header를 덮어씀. 비활성화 시 역할 미리보기 Header는 사내망 시범 테스트 식별값일 뿐 실제 인증으로 간주하지 않음
- 첨부파일은 저장소와 운영 정책이 확정되지 않아 Q&A 작성 범위에서 제외하며, 기존 데이터 이관은 게시판 CRUD 검증 후 별도 Excel·pandas 절차로 수행
- 품질 Agent는 사내 RAG·OpenWebUI의 `gpt-oss-120b` 모델과 대화 DB를 Backend 흐름 및 기존 UI에 연결했으며, Streaming은 적용하지 않음
- 대시보드 조회는 `dashboard_report`에, Report 목록 조회·신규 등록·수정·실제 삭제는 `report_reg`에, Rule&SOP 목록 조회·신규 등록·수정·실제 삭제는 `rulesop`에 연결함. SSO 코드와 DB 세션·권한 저장 구조는 구현했으나 실제 사내 IdP·DB·Spotfire 인증, 나머지 업무 DB·Parquet·공유 폴더 연동과 운영 보안·성능 검증은 후속 작업으로 유지
- 완료된 단계의 상세 근거는 단계 보고서와 디자인 검토 보고서에 증거 스냅샷으로 보존하며 현재 상태 판단에는 개발 계획을 우선함
