# 품질VOE Knox 메일 알림

## 구현 및 검증 범위

2026-09-11 사용자 승인으로 신규 질문·추가 답변 등록 시 메일 알림을 구현했다. 질문·답변 저장이 성공한 뒤 서버에서 비동기로 발송한다. 수정·삭제·상태 변경에는 발송하지 않으며, 메일 실패로 이미 저장된 질문·답변을 취소하지 않는다.

실제 Knox API 응답 규격과 사내망 발송·수신 검증은 사용자 확인 대상이다. 로컬 테스트는 가상 응답으로 요청 구성·재시도·저장과 발송 분리·메일 링크 목적지를 확인한다.

로컬 검증 결과: 메일·Q&A API·저장소·Q&A 계약 테스트, 화면 테스트 15개, 서버 테스트 13개와 배포·내비게이션·범위 계약 테스트 및 프로덕션 빌드 통과. 서버 테스트는 묶음 실행에서 한 차례 실패했으나 해당 파일 분리 실행에서 모두 통과했다. 실제 브라우저·SSO·운영 DB·Knox 발송 통합 검증은 사용자 직접 확인 대상으로 남긴다.

## 서버 설정

`.env.mail.example`을 참고해 환경 소유자가 Git에 저장하지 않는 `.env.mail`을 작성한다. 개발 작업에서는 실제 환경파일을 생성하거나 수정하지 않았다.

| 환경변수 | 설정 |
| --- | --- |
| `KNOX_MAIL_ENABLED` | `true`일 때 발송. 기본 비활성화 |
| `KNOX_MAIL_USER_ID` | API URL의 `userId`에 사용할 개발자 본인의 Knox ID |
| `KNOX_MAIL_TOKEN` | 발급받은 토큰. `Bearer ` 접두어 없이 입력 |
| `KNOX_MAIL_SYSTEM_ID` | 발급받은 System ID |
| `KNOX_MAIL_PORTAL_URL` | 사용자가 접속하는 포털 URL. 하위 경로가 있으면 포함 |
| `KNOX_MAIL_TIMEOUT_MS` | 시도별 제한 시간. 기본 `5000`, 허용 범위 `100`~`30000`ms |

`npm run dev`와 `npm start`는 `.env.mail`이 있으면 읽는다. 설정 후 서버를 재시작한다. `VITE_` 환경변수로 비밀값을 전달하지 않는다.

Docker Compose는 기존 구성에 `-f compose.mail.yaml`을 추가해 실행한다. 예를 들어 SSO 사용 환경에서는 다음 명령으로 운영자가 변경을 반영한다.

```sh
docker compose -f compose.yaml -f compose.sso.yaml -f compose.mail.yaml up -d --build
```

SSO 미사용 환경에서는 `-f compose.sso.yaml`을 제외한다. 이 명령은 배포 안내이며 개발 중 실행하지 않았다. 실제 환경파일은 이미지에 포함하지 않고 컨테이너 실행 시 주입한다.

## 수신 대상과 메일 구성

현재 DB의 `quality_hub_master_account`와 활성 `quality_hub_access_rule` 중 `admin`·`user_id`·`exact` 규칙을 조회한다. 마스터와 개별 등록 관리자를 합쳐 중복을 제거하며 작성자 본인도 포함한다. 사용자 ID는 Knox ID여야 하며 주소는 `{knox_id}@samsung.com`으로 만든다. 수신자 수에 별도 제한을 두지 않는다.

부서 규칙에는 구성원 Knox ID 목록이 없으므로 해당 부서 전체 수신자를 생성할 수 없다. 부서 관리자 규칙이 있으면 `department_recipients_unresolved` 로그를 남기고 개별 등록 관리자·마스터에게 발송한다. 부서 규칙만으로 지정한 관리자까지 포함하려면 구성원 조회 계약이 필요하다.

API URL의 `userId`는 개발자 ID이고, 본문의 `sender.emailAddress`는 질문 또는 추가 답변 작성자 주소다.

- 신규 질문 제목: `[품질 Hub VOE] 게시글 등록:{질문 제목}`
- 추가 답변 제목: `[품질 Hub VOE] 추가 답변: {질문 제목}`
- 본문: 작성자·구분·라인 → 게시글 링크 → 질문 본문. 추가 답변 메일에는 마지막에 새 답변도 표시
- `docSecuType: PERSONAL`, `contentType: TEXT`, 수신자 `recipientType: TO`

메일의 `?qna=open&questionId=숫자` 링크를 열면 데이터 조회 후 해당 질문 상세를 연다. 없는 질문이나 숨긴 질문은 목록과 안내를 보여준다. 일반 텍스트로 문단·줄바꿈을 유지하고 이미지는 게시글에서 확인하라는 문구로 표시한다. 표는 셀 간 탭과 행 간 줄바꿈으로 변환하며 원래 시각적 서식은 보존하지 않는다.

## 실패 처리 및 운영 로그

HTTP 오류(2xx 외 응답), 네트워크 오류와 제한 시간 초과 시 동일 요청을 추가 1회만 보낸다. 설정 오류·DB 조회 실패·수신자 없음은 HTTP 발송 전에 기록하고 종료한다. 토큰·수신 주소·제목·본문·원격 오류 본문은 로그에 남기지 않는다.

| 로그 상태 | 의미 |
| --- | --- |
| `http_accepted_response_unverified` | HTTP 2xx 응답을 받음. 실제 응답 본문·전달 결과는 미검증 |
| `retrying` | 첫 시도 실패, 추가 1회 진행 |
| `failed` | 두 번째 시도까지 실패 |
| `preparation_failed` | 환경변수·Knox ID 형식·DB 조회 등 발송 준비 실패 |
| `skipped_no_recipients` | 개별 등록 관리자·마스터 없음 |
| `skipped_hidden_or_missing` | 발송 조회 시 질문·답변이 없거나 숨김 상태 |
| `department_recipients_unresolved` | 부서 규칙 구성원 목록을 확인할 수 없음 |
| `notification_failed` | 알림 처리 중 예기치 않은 오류 |

실제 응답 구조가 없으므로 응답 본문을 해석하지 않는다. HTTP 2xx 본문이 업무 오류를 뜻하는 경우에는 현재 재시도하지 않는다. 사용자가 실제 성공·실패 응답을 확인한 뒤 판정 규칙을 보완해야 한다.

비동기 작업은 서버 메모리에서 관리하며 DB 발송 큐는 추가하지 않았다. 정상 종료 시 Q&A API는 진행 중 작업을 기다리지만, 서버 강제 종료·프로세스 장애·종료 유예시간 초과에는 미발송 작업이 유실될 수 있다. 기본 5초 설정은 두 번의 HTTP 시도를 약 10초 이내로 제한한다. 응답 유실·시간 초과 후 재시도는 동일 메일을 중복 전달할 수 있으며, Knox의 중복 방지 규격은 미수령이다.

## 사내망 직접 확인

1. 환경변수를 설정하고 메일 기능을 활성화한다. DB 권한 관리에 수신할 관리자·마스터의 실제 Knox ID를 등록한다.
2. 일반 사용자가 줄바꿈이 있는 질문을 등록해 저장 완료, 신규 등록 제목, 발신자, 관리자·마스터 수신과 본문을 확인한다.
3. 관리자 또는 마스터 본인이 추가 답변을 등록해 본인 수신, 추가 답변 제목과 질문 원문·새 답변 표시를 확인한다.
4. 메일 링크에서 해당 질문 상세가 열리는지 확인한다. 로그인 전 접근이라면 로그인 후에도 링크 목적지가 유지되는지 확인한다.
5. 오류 시험은 분리된 시험 설정에서 진행하고, 서버 로그에서 최대 두 번 시도와 게시글 저장 유지를 확인한다. 정상 설정을 복원한다.
6. 실제 성공·실패 HTTP 상태와 응답 본문을 확인한다. 공유할 때 토큰과 개인·업무 내용은 제거한다. 2xx 응답이 접수인지 전달 완료인지 확인한다.
