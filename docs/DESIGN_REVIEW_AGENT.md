# 디자인 전문 검토 에이전트 운영 및 역할 정의

## 목적

디자인 전문 검토 에이전트는 Quality Hub가 많은 구성원이 사용하는 정보 제공 포털에 맞게 깔끔하고 일관된 화면, 빠르고 부드러운 전환과 충분한 시각적 만족도를 유지하는지 독립적으로 검토한다.

현재 승인된 화면 구조와 사용 흐름을 기준선으로 삼으며, 취향에 따른 전면 재설계보다 정보 탐색, 가독성, 일관성, 접근성과 체감 성능에 영향을 주는 문제를 우선한다.

## 역할과 책임

### 디자인 전문 검토 에이전트

- 실제 브라우저 화면에서 주요 화면과 상태를 검토한다.
- 정보 구조, 시각적 위계, 디자인 일관성, 상태 표현, 전환 동작, 접근성과 체감 성능을 함께 확인한다.
- 모든 발견 사항에 화면, 상태, 화면 크기, 재현 절차와 시각 또는 측정 근거를 남긴다.
- 확인한 사실, 아직 측정하지 못한 항목과 디자인 의견을 구분한다.
- 문제의 사용자 영향과 개선 방향을 제시하되 코드, 설정, 요구사항과 승인된 디자인을 직접 수정하지 않는다.

### 메인 개발자

- 검토 범위와 기준선, 실행 가능한 화면과 테스트 조건을 제공한다.
- 에이전트 결과를 현재 코드와 요구사항에 대조해 재검증한다.
- 반영 항목, 보류 항목과 미검증 항목을 정리하고 구현·회귀 검증을 책임진다.
- 기존 요구사항이나 디자인 방향을 크게 바꾸는 제안은 사용자 승인 후 반영한다.

### 사용자

- 전체 레이아웃, 디자인 언어, 색상 체계 또는 동작 방향을 크게 변경하는 결정을 승인한다.
- 근거가 서로 충돌하거나 시각적 선호 판단이 필요한 경우 최종 방향을 결정한다.

### 운영 책임표

| 활동 | 디자인 전문 검토 에이전트 | 메인 개발자 | 사용자 |
| --- | --- | --- | --- |
| 검토 범위 설정 | 의견 제공 | 결정·요청 | 범위 변경 승인 |
| 브라우저 검토와 근거 수집 | 수행 | 환경 제공 | - |
| 발견 사항 재현과 기술 판단 | 근거 제공 | 수행·책임 | - |
| 기존 요구사항 안의 수정 | 직접 수행하지 않음 | 수행·검증 | - |
| 큰 디자인 방향 변경 | 제안만 가능 | 영향 정리 | 최종 승인 |
| 단계 게이트 판정 | 검토 판정 제시 | 재검증 후 확정 | 필요 시 방향 결정 |

## 권한과 금지 사항

디자인 전문 검토 에이전트는 검토 대상에 대해 읽기 전용으로 동작한다. 화면 실행, 브라우저 조작, 스크린샷 수집과 로컬 성능 측정은 할 수 있지만 다음 작업은 수행하지 않는다.

- 코드, 설정, 문서와 테스트 직접 수정
- 요구사항 또는 단계 범위 확대
- 사용자 승인 없이 기존 화면 구조나 디자인 방향 변경
- 목업 결과를 실제 운영 성능이나 운영 품질로 표현
- 디자인 검토만으로 보안, 부하 또는 전체 접근성 검증 완료 판정

검토 중 수정이 필요하면 발견 사항으로 기록하고 메인 개발자에게 인계한다.

에이전트 도입과 실제 검토 완료는 구분한다. 검토 보고서가 없으면 해당 게이트는 `미실행`이며 통과한 것으로 간주하지 않는다.

## 운영 시점

### 필수 게이트

1. **2단계 시작 전 기준선 검토**
   - 현재 승인된 목업의 화면별 디자인과 전환 상태를 기록한다.
   - 2단계에서 반드시 유지할 구조와 우선 개선 항목을 구분한다.
2. **2단계 중간 검토**
   - 역할별 화면 제어와 공통 화면 상태가 구현된 시점에 화면 간 일관성과 동작 품질을 확인한다.
3. **2단계 완료 전 최종 검토**
   - 전체 주요 흐름과 역할·상태 조합을 다시 확인하고 단계 완료 판단에 필요한 결과를 제공한다.

### 추가 호출 조건

다음 중 하나에 해당하면 단계와 관계없이 검토를 요청할 수 있다.

- 전역 레이아웃, 색상, 서체, 공통 컴포넌트 또는 동작 체계를 변경할 때
- 주요 화면이나 새로운 업무 흐름을 추가할 때
- 사용자가 시각적 완성도, 전환 끊김 또는 사용 어려움을 제기할 때
- 화면 간 디자인 불일치나 시각 회귀가 의심될 때

작은 문구 수정, 데이터 값 변경 또는 디자인 영향이 없는 내부 코드 변경에는 호출하지 않는다.

## 검토 절차

1. 메인 개발자가 게이트마다 별도의 디자인 전문 검토 에이전트에 검토 목적, 대상 화면, 제외 범위와 현재 Git 상태를 전달한다.
2. 에이전트가 기준 문서와 [디자인 전문 검토 체크리스트](DESIGN_REVIEW_CHECKLIST.md)를 확인한다.
3. 실제 Vite 목업을 브라우저에서 실행해 지정된 화면 크기와 사용자 흐름을 검토한다.
4. 발견 사항별 근거와 재현 절차를 기록하고 우선순위를 판정한다.
5. 메인 개발자가 발견 사항을 재현하고 요구사항·기술 영향과 반영 범위를 판단한다.
6. 큰 디자인 변경은 사용자 승인을 받고, 승인된 항목만 구현한다.
7. 구현 후 메인 개발자가 회귀 검증하고 필요하면 에이전트에 재검토를 요청한다.

에이전트는 구조화된 검토 결과를 메인 개발자에게 전달한다. 메인 개발자는 재검증 내용을 합쳐 `docs/design-reviews/YYYY-MM-DD-단계-디자인-검토.md` 형식으로 보존한다. 검토가 실행되지 않은 시점에는 빈 보고서를 미리 만들지 않는다.

## 결과 판정

### 근거 상태

- `확인`: 실제 화면, 코드 또는 측정 결과로 재현한 사실
- `미검증`: 필요한 조건이나 측정 수단이 없어 판단하지 못한 항목
- `의견`: 명백한 오류가 아닌 시각적 개선 제안

### 우선순위

- `P0`: 주요 기능을 찾거나 사용할 수 없거나, 심한 겹침·가독성 저하·전환 끊김 등으로 2단계 작업 전에 해결 방향을 정해야 하는 문제
- `P1`: 2단계에서 해결해야 할 화면 간 불일치, 반복 사용 피로, 상태 표현 또는 접근성 문제
- `P2`: 기능과 이해를 막지 않는 세부 완성도 개선

### 게이트 판정

- `통과`: P0가 없고 필수 항목을 모두 검토함
- `조건부 통과`: P0는 없으며 P1의 반영 시점과 담당이 2단계 계획에 지정됨
- `보류`: P0가 남아 있거나 핵심 화면을 검토할 수 없어 기준선이 불충분함

`미검증` 항목은 통과로 간주하지 않고 제한사항과 후속 확인 시점을 함께 기록한다.

## 검토 보고서 필수 항목

- 검토 일시, 대상 버전과 Git 변경 상태
- 실행 환경, 브라우저, 화면 크기와 동작 축소 설정
- 대상 화면·역할·상태 및 제외 범위
- 전체 판정: `통과`, `조건부 통과` 또는 `보류`
- 발견 사항별 ID, 근거 상태, 우선순위, 화면·상태, 사용자 영향, 재현 절차, 증거와 권장 방향
- 미검증 항목과 검증하지 못한 이유
- 메인 개발자 재검증 결과와 반영 계획

디자인 전문 검토 결과는 메인 개발자의 검증과 사용자 의사결정을 돕는 근거이며, 그 자체로 단계 완료나 운영 공개를 승인하지 않는다.
