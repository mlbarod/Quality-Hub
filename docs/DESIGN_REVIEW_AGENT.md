# 디자인 전문 검토 에이전트 운영 및 역할 정의

## 목적

디자인 전문 검토 에이전트는 Quality Hub가 많은 구성원이 사용하는 정보 제공 포털에 맞게 깔끔하고 일관된 화면, 빠르고 부드러운 전환과 충분한 시각적 만족도를 유지하는지 독립적으로 검토한다.

현재 승인된 화면 구조와 사용 흐름을 기준선으로 삼으며, 취향에 따른 전면 재설계보다 정보 탐색, 가독성, 일관성, 접근성과 체감 성능에 영향을 주는 문제를 우선한다.

검수 강도는 기능 개수나 CSS 적용 범위가 아니라 실제 사용자 영향, 화면 간 결합도와 회귀 위험으로 결정한다. 기능 개발마다 관성적으로 독립 전체 검수를 반복하지 않고, 필요한 가장 작은 범위의 검증으로 품질 근거를 확보한다.

기존 방향을 유지한다는 이유로 글자 크기, 구성 비율, 정렬, 여백, 이미지와 배경의 조화, 장식 요소의 침범을 취향 문제로만 낮추지 않는다. 구조를 바꾸지 않는 범위에서도 사용자가 불편하거나 완성도가 낮다고 느낄 수 있는 시각적 원인을 구체적인 근거와 함께 판정한다.

## 영구 에이전트 설정

- 프로젝트 커스텀 에이전트 이름: `design_reviewer`
- 설정 파일: [`.codex/agents/design-reviewer.toml`](../.codex/agents/design-reviewer.toml)
- 권한: `sandbox_mode = "read-only"`
- 모델: 특정 모델을 고정하지 않고 메인 세션 설정을 상속
- 추론 수준: `high`

독립 전체 검수 조건이나 독립 범위 검수 호출 조건에 해당하면 메인 개발자는 `design_reviewer`에 검토를 위임한다. 설정 파일의 존재는 에이전트 도입만 의미하며 실제 검토 완료를 의미하지 않는다. 기능 검증과 메인 UI 범위 확인은 독립 디자인 게이트와 구분한다.

## 역할과 책임

### 디자인 전문 검토 에이전트

- 실제 브라우저 화면에서 주요 화면과 상태를 검토한다.
- 정보 구조, 시각적 위계, 디자인 일관성, 상태 표현, 전환 동작, 접근성과 체감 성능을 함께 확인한다.
- 선택한 검토 범위의 화면 균형을 먼저 확인한 뒤 카드·버튼·팝업 등 변경 컴포넌트를 1:1 확대해 글자, 간격, 정렬, 내부 이미지와 배경을 별도로 확인한다.
- 요소 본체뿐 아니라 pseudo-element, 링, outline, 그림자와 hover·focus transform을 포함한 최종 시각 영역을 기준으로 겹침과 잘림을 판단한다.
- 모든 발견 사항에 화면, 상태, 화면 크기, 재현 절차와 시각 또는 측정 근거를 남긴다.
- 확인한 사실, 아직 측정하지 못한 항목과 디자인 의견을 구분한다.
- 문제의 사용자 영향과 개선 방향을 제시하되 코드, 설정, 요구사항과 승인된 디자인을 직접 수정하지 않는다.

### 메인 개발자

- 검토 범위와 기준선, 실행 가능한 화면과 테스트 조건을 제공한다.
- 현재 커밋 SHA와 미커밋 변경 파일, 디자인 관련 diff 식별값을 기록해 검토 결과가 정확히 어떤 상태를 대상으로 하는지 고정한다.
- 에이전트 결과를 현재 코드와 요구사항에 대조해 재검증한다.
- 반영 항목, 보류 항목과 미검증 항목을 정리하고 구현·회귀 검증을 책임진다.
- 독립 검토를 실행한 범위의 `미실행`, `보류` 또는 필수 `미검증`을 메인 개발자 단독 확인으로 상향 판정하지 않는다. 해당 판정은 검토 대상으로 정한 화면·흐름 또는 전체 게이트에만 적용하며, 범위 밖 기능 완료를 자동으로 막지 않는다.
- 기존 요구사항이나 디자인 방향을 크게 바꾸는 제안은 사용자 승인 후 반영한다.

### 사용자

- 전체 레이아웃, 디자인 언어, 색상 체계 또는 동작 방향을 크게 변경하는 결정을 승인한다.
- 근거가 서로 충돌하거나 시각적 선호 판단이 필요한 경우 최종 방향을 결정한다.

### 운영 책임표

| 활동 | 디자인 전문 검토 에이전트 | 메인 개발자 | 사용자 |
| --- | --- | --- | --- |
| 검토 범위 설정 | 의견 제공 | 결정·요청 | 범위 변경 승인 |
| 브라우저 검토와 근거 수집 | 수행 | 환경 제공 | - |
| 발견 사항 재현과 기술 판단 | 근거 제공 | 수행·책임 | - |
| 기존 요구사항 안의 수정 | 직접 수행하지 않음 | 수행·검증 | - |
| 큰 디자인 방향 변경 | 제안만 가능 | 영향 정리 | 최종 승인 |
| 단계 게이트 판정 | 검토 판정 제시 | 재검증 후 확정 | 필요 시 방향 결정 |

### 검수 브리프

독립 검수 전에 메인 개발자는 아래 정보를 한 번에 제공한다. 독립 범위 검수에서는 이 브리프와 선택된 체크 항목을 작업 기준으로 사용하며, 리뷰어가 프로젝트 전체 문서와 체크리스트 전부를 다시 해석해 범위를 정하지 않는다.

- 검수 유형과 프리셋: `component`, `flow`, `layer`, `motion`, `full`
- 목적, 대상 화면·상태, 제외 범위와 선택한 체크리스트 항목
- 현재 커밋 SHA, 미커밋 변경 파일과 디자인 관련 diff 식별값
- 정상 응답을 확인한 URL·포트, 서버 작업 폴더와 준비 완료 selector
- 대상 화면 진입 경로, 필요한 역할·가상 데이터 상태와 비교 기준선
- 이전 근거 중 만료되는 항목과 계속 유효한 항목

독립 범위 검수는 메인이 제공한 정상 서버를 재사용하고 서버 재시작·프로덕션 빌드·별도 성능 측정을 기본 작업에 포함하지 않는다. 연결 전 확인에 실패하면 문서의 재시도 기준을 적용한다.

## 권한과 금지 사항

디자인 전문 검토 에이전트는 검토 대상에 대해 읽기 전용으로 동작한다. 화면 실행, 브라우저 조작, 스크린샷 수집과 로컬 성능 측정은 할 수 있지만 다음 작업은 수행하지 않는다.

- 코드, 설정, 문서와 테스트 직접 수정
- 요구사항 또는 단계 범위 확대
- 사용자 승인 없이 기존 화면 구조나 디자인 방향 변경
- 목업 결과를 실제 운영 성능이나 운영 품질로 표현
- 디자인 검토만으로 보안, 부하 또는 전체 접근성 검증 완료 판정

검토 중 수정이 필요하면 발견 사항으로 기록하고 메인 개발자에게 인계한다.

에이전트 도입과 실제 검토 완료는 구분한다. 독립 전체 검수 보고서가 없으면 해당 전체 게이트는 `미실행`이며 통과한 것으로 간주하지 않는다.

검토 결과는 기록된 커밋 SHA, 미커밋 변경 상태와 명시된 검토 범위에 유효하다. 이후 변경이 검토한 화면·상태·공통 계약에 영향을 줄 때만 해당 근거를 `만료`로 표시한다. 범위 밖 데이터·기능·문서 변경이나 서로 독립적인 화면 변경은 기존 근거 전체를 만료시키지 않는다. 전체 게이트 결과는 검토한 주요 화면·공통 계약에 디자인 영향 변경이 생기면 영향받은 항목을 재검토한다.

## 검증·검수 유형과 선택 기준

공식 검증·검수 명칭은 `기능 검증`, `메인 UI 범위 확인`, `독립 범위 검수`, `독립 전체 검수`다. 결과에도 수행자가 불분명한 `범위 검수 완료` 대신 실제 수행 유형을 기록한다. 기능 수가 많거나 전역 토큰을 사용한다는 사실만으로 독립 전체 검수를 선택하지 않는다.

### 기능 검증

다음 작업은 메인 개발자가 자동 테스트와 필요한 기능 브라우저 검증으로 확인하며 디자인 전문 검토 에이전트를 호출하지 않는다.

- 데이터, API, 저장, 권한과 내부 상태 로직 변경
- CRUD, 검색, 알림과 편집기 등 기능 동작 수정
- 문구·라벨·예시 데이터 변경
- 기존 배치·크기·시각적 위계에 영향을 주지 않는 버그 수정
- 테스트·빌드·문서·개발 도구 변경

### 메인 UI 범위 확인

한 화면, 한 컴포넌트 또는 직접 연결된 교차 상태에 국한된 변경은 메인 개발자가 변경 화면과 인접 영향만 확인한다.

- 버튼·카드·팝업의 위치, 크기, 간격 또는 이름 변경
- 한 화면의 정보 위계나 상태 표현 변경
- 특정 전체 화면과 헤더 메뉴, 팝업과 배경처럼 직접 겹치는 레이어 수정
- 단순 색상 토큰 교체: 대비와 의미 색상을 자동 검사하고 대표 컴포넌트만 확인
- 서체 교체: 대표 화면의 줄바꿈·잘림·로딩을 확인하고 문제가 발견될 때만 범위를 확대
- 여러 기능이 같은 화면 또는 같은 업무 흐름 안에서 변경된 경우의 묶음 확인

### 독립 범위 검수

메인 UI 범위 확인 대상 중 다음 하나에 해당할 때만 `design_reviewer`에 독립 범위 검수를 요청한다.

- 사용자가 독립 디자인 검수를 명시적으로 요청
- 사용자가 독립 재검수를 명시적으로 요청했거나, 사용자 지적을 메인이 재현한 결과 판단이 불확실한 P0·P1 또는 공통 디자인 계약 영향으로 분류
- 메인 개발자가 시각적 판정을 확신하기 어렵거나 독립 근거가 필요한 P0·P1 후보
- 독립 전체 검수에서 발견한 문제를 수정한 뒤 해당 항목만 독립 재검토할 필요가 있음

메인 UI 범위 확인과 독립 범위 검수는 각각 UI 검수를 10분 이내에 완료하도록 권장한다. 10분은 강제 상한이 아니며, 변경과 직접 관련된 필수 확인이 남아 있으면 10분을 초과해 계속할 수 있다.

이 시간 기준은 코드 작성·기능 구현·수정 및 자동 테스트 실행을 제외한 UI 검수 시간에 적용한다. 검수 대상 선정, 브라우저 확인, 근거 수집과 결과 정리는 UI 검수 시간에 포함한다. 환경 준비 실패나 10분 초과는 독립 전체 검수 승격 사유가 아니다. 10분을 초과한 뒤에도 변경과 직접 관련된 항목만 확인하며, 관련 없는 화면·상태로 범위를 확대하지 않는다. 환경 준비에 실패하면 반복 실행으로 시간을 늘리지 않고 확인된 결과와 `미검증` 항목을 분리해 보고한다.

### 독립 전체 검수

주요 업무 영역은 `홈/App 허브`, `대시보드`, `Report`, `통합 검색`, `Rule&SOP`, `Q&A`, `품질 Agent`, `사용자 및 권한`의 8개로 구분한다. 같은 영역의 목록·상세·작성·팝업·hover·focus·권한별 상태는 하나의 업무 영역에 연결된 상태로 계산하며, 변경 파일이나 컴포넌트 개수를 업무 영역 수로 계산하지 않는다.

공통 디자인 계약은 여러 업무 영역에서 동일하게 지켜야 하는 컴포넌트 구조·배치 기하·크기·클릭 영역·상호작용·키보드와 초점·상태 의미·오버레이와 내비게이션 동작 규칙이다. 공통 파일이나 전역 selector를 수정했다는 사실만으로 공통 디자인 계약 변경으로 판정하지 않는다. 의미와 대비를 유지하는 색상값, 배치·크기·클릭 영역에 영향을 주지 않는 테두리·모서리·그림자 또는 특정 업무 영역에만 실제 적용되는 변경은 독립 전체 검수 사유가 아니다.

다음 중 하나에 해당할 때만 독립 전체 검수를 수행한다.

- 새로운 최상위 화면 또는 주요 업무 흐름을 추가
- 전역 헤더·내비게이션·레이아웃·반응형 기준·레이어 체계를 구조적으로 변경
- 공통 컴포넌트의 구조·크기·상호작용 계약을 바꿔 4개 이상의 주요 업무 영역에 영향을 줌
- 단순 값 교체가 아니라 상태 색상의 의미, 전체 테마 체계 또는 시각적 위계를 재설계
- 글자 크기·행간·글꼴 메트릭 등 타이포그래피 기하를 바꿔 4개 이상의 주요 업무 영역 배치에 영향을 줌
- 4개 이상의 주요 업무 영역에서 핵심 키보드·접근성·역할별 업무 흐름을 구조적으로 변경
- 사용자가 독립 전체 검수를 명시적으로 요청

공통 계약 변경이 1~3개 주요 업무 영역에 영향을 주면 독립 범위 검수로 확인한다. `4개 이상` 기준은 하나의 공통 디자인 계약 변경이 동시에 영향을 주는 경우에만 적용하며 서로 무관한 국소 변경을 합산하지 않는다. 기준선·중간·최종 3회 검수는 전역 재설계처럼 장기간 진행되는 대형 디자인 작업에만 적용한다.

단계 완료 시 전체 회귀 테스트와 프로덕션 빌드는 수행하지만 단계 완료 자체는 독립 전체 검수 사유가 아니다. 마지막 유효 근거 이후 위 조건에 해당하는 변경이 있을 때만 독립 전체 검수를 수행한다. 디자인 변경이 없거나 기존 근거가 유효하거나 각 국소 변경이 메인 UI 범위 확인 또는 필요한 독립 범위 검수를 마쳤다면 다시 수행하지 않는다.

메인 UI 범위 확인이나 독립 범위 검수 중 예상하지 못한 4개 이상 주요 업무 영역의 회귀, 공통 계약 변경 또는 위의 구조적 조건이 확인되면 독립 전체 검수로 승격한다. 기능 개수, 변경 파일 수, `전역`이라는 명칭, 환경 준비 실패 또는 검수 시간만으로 승격하지 않는다.

## 검토 절차

이 절은 디자인 전문 검토의 수행 순서를 정하는 단일 기준이다. 에이전트 설정 파일은 이 절을 참조하며 별도의 검토 절차를 중복 정의하지 않는다.

1. 메인 개발자가 변경의 사용자 영향, 화면 간 결합도와 공통 계약 변경 여부를 근거로 `기능 검증`, `메인 UI 범위 확인`, `독립 범위 검수`, `독립 전체 검수` 중 하나를 먼저 선택한다.
2. 기능 검증은 관련 자동 테스트와 필요한 기능 브라우저 검증만 수행하고 디자인 게이트 판정을 만들지 않는다.
3. 메인 UI 범위 확인은 메인 개발자가 변경 화면·상태와 직접 연결된 UI/UX 기준만 확인하며 정식 독립 검수 체크리스트나 디자인 게이트 판정을 만들지 않는다.
4. 독립 범위 검수가 필요한 경우 메인 개발자가 `design_reviewer`에 검수 브리프와 정상 응답을 확인한 화면 URL을 전달한다. 리뷰어는 지정된 프리셋과 [디자인 전문 검토 체크리스트](DESIGN_REVIEW_CHECKLIST.md) 항목만 수행하고 기준선·중간·최종 검수, 서버 재시작과 전체 빌드로 확대하지 않는다.
5. 독립 전체 검수는 `design_reviewer`가 1920×1080, 100%, DPR 1을 먼저 확인하고, 변경한 반응형 기준 또는 실제 배포 대상에 필요한 화면 크기만 추가한다. 주요 화면과 공통 계약에 해당하는 체크리스트 항목을 수행한다.
6. 동작 축소는 모션·전환 변경 시, 역할별 상태는 권한·노출 변경 시, 전체 오버레이 교차표는 전역 내비게이션·레이어 변경 시처럼 변경 위험과 연결된 검증만 수행한다.
7. 독립 범위 검수는 브라우저 자동화가 중단되면 자동 재실행하지 않고 확인된 결과와 `미검증`을 즉시 반환한다. 독립 전체 검수는 30분 총시간 안에서 환경 정리 후 1회만 재시도하며, 재시도가 별도의 추가 30분을 만들지 않는다.
8. 발견 사항별 근거와 재현 절차를 기록하고 우선순위를 판정한다. 자동 접근성 검사, DOM 측정과 육안 검토 결과를 구분한다.
9. 메인 개발자는 독립 근거를 코드·요구사항과 대조하고 P0·P1, 근거가 불명확한 항목과 실제 반영 항목만 직접 재현한다. 이미 통과한 항목 전체를 반복 실행하지 않으며 독립 검토 판정은 그 검토 범위 안에서만 유지한다.
10. P0·P1 수정 후에는 영향받은 항목만 재검토한다. 수정이 독립 전체 검수 조건에 해당하지 않으면 독립 전체 검수를 다시 실행하지 않는다.

에이전트는 구조화된 검토 결과와 필요한 임시 스크린샷·측정 산출물을 메인 개발자에게 전달한다. 독립 범위 검수는 대상·판정·미검증 항목을 작업 결과에 간결하게 남기며 별도 정식 보고서와 전체 화면 스크린샷을 의무화하지 않는다. 독립 전체 검수만 메인 개발자가 재검증 내용을 합쳐 `docs/design-reviews/YYYY-MM-DD-단계-디자인-검토.md` 형식으로 보존하고, 공식 근거를 `docs/design-reviews/assets/` 아래에 연결한다. 검토가 실행되지 않은 시점에는 빈 보고서를 만들지 않는다.

## 검수 기준 튜닝

사용자가 검토 누락·오판·방향 불일치를 지적하면 메인 개발자가 재현해 분류한다. 일회성 내용은 해당 검토 보고서에만 기록하고, 재사용할 기준만 이 문서 또는 체크리스트와 계약 테스트에 반영한다. 반영한 기준은 다음 독립 검토에서 확인하며 중복되거나 효과 없는 기준은 정리한다.

## 결과 판정

### 근거 상태

- `확인`: 실제 화면, 코드 또는 측정 결과로 재현한 사실
- `미검증`: 필요한 조건이나 측정 수단이 없어 판단하지 못한 항목
- `의견`: 명백한 오류가 아닌 시각적 개선 제안

### 우선순위

- `P0`: 주요 기능을 찾거나 사용할 수 없거나, 심한 겹침·가독성 저하·전환 끊김 등으로 작업을 계속하기 전에 해결 방향을 정해야 하는 문제
- `P1`: 현재 작업 범위에서 해결해야 할 화면 간 불일치, 반복 사용 피로, 상태 표현 또는 접근성 문제
- `P2`: 기능과 이해를 막지 않는 세부 완성도 개선

### 게이트 판정

- `통과`: P0가 없고 필수 항목을 모두 독립 검토했으며 해결되지 않은 P1이 없음
- `조건부 통과`: 필수 항목을 모두 독립 검토했고 P0는 없으며, 남은 P1의 영향·담당·반영 시점과 재검토 계획이 지정됨
- `보류`: P0가 남아 있거나, 대상 상태가 현재 변경과 일치하지 않거나, 독립 검토가 중단됐거나, 핵심 화면·필수 조건이 `미검증`이어서 근거가 불충분함

선택한 검토 범위의 필수 항목이 `미검증`이면 그 범위 안에서는 통과로 간주하지 않고 제한사항을 기록한다. 검토 대상으로 선택하지 않은 화면·조건은 범위 밖이며 다른 기능의 완료를 자동으로 막지 않는다. 메인 개발자는 독립 검토의 판정을 해당 범위에서 유지하거나 더 엄격하게 조정할 수 있지만, 독립 재검토 없이 그 범위의 `보류`를 `조건부 통과`나 `통과`로 상향할 수 없다.

## 독립 전체 검수 보고서 필수 항목

- 검토 일시, 대상 커밋 SHA, 미커밋 변경 파일과 디자인 관련 diff 식별값
- 보고서의 현재 상태: `유효` 또는 디자인 영향 변경으로 인한 `만료`
- 실행 환경, 브라우저, 화면 크기와 동작 축소 설정
- 대상 화면·역할·상태 및 제외 범위
- 전체 판정: `통과`, `조건부 통과` 또는 `보류`
- 필수 체크리스트의 항목별 `통과`, `실패`, `미검증`, `해당 없음` 결과
- 1920×1080과 실제로 검증한 선택 해상도별 전체 화면 및 변경 컴포넌트 확대 스크린샷, 측정값과 보존 경로
- 발견 사항별 ID, 근거 상태, 우선순위, 화면·상태, 사용자 영향, 재현 절차, 증거와 권장 방향
- 미검증 항목과 검증하지 못한 이유
- 독립 검토 판정과 메인 개발자 재검증 판정을 분리한 결과 및 반영 계획

디자인 전문 검토 결과는 메인 개발자의 검증과 사용자 의사결정을 돕는 근거이며, 그 자체로 단계 완료나 운영 공개를 승인하지 않는다.
