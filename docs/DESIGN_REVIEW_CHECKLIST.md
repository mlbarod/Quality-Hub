# 디자인 전문 검토 체크리스트

## 사용 방법

각 항목을 `통과`, `실패`, `미검증`, `해당 없음`으로 기록한다. `실패`와 `미검증`에는 대상 화면, 재현 절차와 근거를 함께 남긴다. 코드만 읽고 화면 품질을 통과로 판정하지 않는다. 해상도 검증은 1920×1080을 가장 먼저 수행하는 필수 기준으로 삼고, 1440×900과 1366×768은 시간과 실행 환경에 따라 생략할 수 있는 선택 기준으로 삼는다. 생략한 선택 해상도는 검토 제외 범위와 이유를 기록하며 그 자체로 게이트를 `보류`하지 않는다.

## 1. 검토 준비

- [ ] 검토 목적, 대상 단계와 제외 범위를 확인했다.
- [ ] 현재 커밋 SHA, 미커밋 변경 파일과 디자인 관련 diff 식별값을 기록했다.
- [ ] 최신 디자인 영향 변경 이후 작성된 검토인지 확인하고, 대상 상태가 다르면 이전 보고서를 `만료`로 표시했다.
- [ ] 목업 데이터와 실제 연동 상태를 구분했다.
- [ ] 관련 요구사항, UI/UX 기준과 현재 단계 완료 보고서를 확인했다.
- [ ] Vite 목업을 실제 브라우저에서 열었다.
- [ ] **[필수·최우선]** 1920×1080 화면을 100% 배율과 DPR 1로 확인했다.
- [ ] **[선택]** 1440×900 화면을 100% 배율과 DPR 1로 확인했다.
- [ ] **[선택]** 1366×768 화면을 100% 배율과 DPR 1로 확인했다.
- [ ] 서체·크기·배치 변경은 125% 확대에서도 잘림, 겹침과 기능 손실이 없는지 추가 확인했다.
- [ ] 일반 동작과 `prefers-reduced-motion: reduce` 환경을 각각 확인했다.
- [ ] 1920×1080과 실제로 검증한 선택 해상도의 전체 화면 및 변경 컴포넌트 1:1 확대 스크린샷을 수집했다.

## 2. 주요 화면과 흐름

- [ ] 대시보드에서 핵심 상태와 주요 업무 진입점을 바로 이해할 수 있다.
- [ ] 통합 검색 결과에서 Report, Rule&SOP와 Q&A 대상 콘텐츠로 이동할 수 있다.
- [ ] Report 카탈로그, 필터, 원본 화면 영역과 관리 동작의 위계가 명확하다.
- [ ] Rule&SOP 분류, 필터, 카드, 상세와 관리 흐름을 설명 없이 사용할 수 있다.
- [ ] Q&A 목록, 상세, 작성, 답변, 상태와 최종 답변 흐름이 자연스럽다.
- [ ] 품질 Agent 패널과 전체 화면의 진입·복귀 및 참조 정보 구조가 명확하다.
- [ ] 사용자 및 권한 화면에서 역할, 규칙과 위험한 관리 동작을 구분할 수 있다.
- [ ] 주요 화면 이동 후 제목, 현재 위치와 돌아가기 동작을 쉽게 찾을 수 있다.

## 3. 정보 구조와 시각적 위계

- [ ] 화면의 제목, 핵심 정보, 보조 정보와 조작 요소의 우선순위가 분명하다.
- [ ] 첫 화면에서 사용자가 다음에 할 일을 쉽게 판단할 수 있다.
- [ ] 카드와 표의 정보 밀도가 지나치게 높거나 낮지 않다.
- [ ] 긴 제목, 설명, 사용자 ID와 상태 문구가 겹치거나 잘리지 않는다.
- [ ] 사용자가 읽어야 하는 본문·설명·상태·배지는 계산된 글자 크기 12px 이상이고, 주요 제목·텍스트 버튼은 14px 이상이다.
- [ ] 주요 텍스트 버튼은 높이 40px 이상이며 글자와 아이콘의 수직 정렬이 일관된다.
- [ ] 중요한 상태와 위험한 동작이 주변 정보에 묻히지 않는다.
- [ ] 데이터 출처, 최신 시각, 목업 여부와 오류 상태를 오해하지 않는다.

## 4. 디자인 시스템 일관성

- [ ] 전체 화면의 색상, 서체, 여백, 테두리, 모서리와 그림자 규칙이 일관된다.
- [ ] 기본·강조·보조·위험 버튼의 의미와 모양이 화면마다 같다.
- [ ] 검색, 필터, 입력, 선택, 팝업, 카드와 상태 배지의 사용 방식이 일관된다.
- [ ] Dashboard·Report·Rule&SOP·Agent·Q&A·권한 화면 사이에 시각적 단절이 없다.
- [ ] 완료·경고·오류 색상은 브랜드 강조색과 구분되고 의미가 유지된다.
- [ ] 아이콘의 크기, 선 굵기, 정렬과 의미가 일관된다.
- [ ] hover, focus, active, selected, disabled 상태가 서로 명확히 구분된다.

## 5. App 허브와 내부 미니 화면

- [ ] **[선택·1366×768 검증 시]** 홈에서 헤더, 핵심 소개, 네 App과 중앙 Agent를 불필요한 가로·세로 스크롤 없이 첫 화면에서 사용할 수 있다.
- [ ] 1920×1080과 실제로 검증한 선택 해상도에서 네 App의 계산된 크기·좌표·상호 간격과 중앙 Agent의 크기·간격을 표로 기록했다.
- [ ] App 카드 제목·설명·상태 배지의 계산된 글자 크기와 줄 수를 카드별로 확인했다.
- [ ] 카드와 Agent의 겹침 검사는 본체뿐 아니라 pseudo-element, 외곽 링, outline, hover·focus transform과 콘텐츠를 가리는 그림자를 포함한다.
- [ ] 기본·hover·focus 상태에서 장식 요소가 인접 카드의 테두리, 글자, 내부 미니 화면이나 이동 아이콘을 침범하지 않는다.
- [ ] 네 App의 내부 미니 화면은 같은 안전 영역, 안쪽 여백, 모서리와 배경 계층을 사용하고 카드 제목·상태·이동 아이콘을 가리지 않는다.
- [ ] 내부 미니 화면의 핵심 도형이 잘리거나, 빈 여백이 한쪽으로 치우치거나, 배경이 주변 카드와 분리된 이미지처럼 떠 보이지 않는다.
- [ ] 원본 UI를 축소 재사용한 경우 transform 적용 뒤의 실제 표시 크기, 잘림 영역과 최소 시각 요소 크기를 기록했다.
- [ ] 장식용 마이크로 텍스트는 정보 전달이나 가독성 통과 근거로 사용하지 않고, 자동 접근성 검사 0건을 시각적 조화 통과 근거로 대체하지 않았다.
- [ ] 긴 App 제목·설명·상태 문구를 넣어도 헤더, 배지와 내부 미니 화면이 충돌하지 않는다.

## 6. 역할과 공통 화면 상태

2단계 구현 이후에는 아래 항목을 마스터, 관리자, 일반유저와 접근 차단 사용자별로 확인한다.

- [ ] 역할에 맞지 않는 메뉴와 조작이 노출되거나 활성화되지 않는다.
- [ ] 권한 없음 안내가 역할별 문의 대상을 정확히 표시한다.
- [ ] 로딩 상태가 기존 레이아웃을 불필요하게 흔들지 않고 대상 가까이에 표시된다.
- [ ] 데이터 없음 팝업이 작업을 막지 않고 명확하게 닫힌다.
- [ ] 조회 오류 문구와 `다시 시도` 동작을 쉽게 찾을 수 있다.
- [ ] 오래된 데이터와 마지막 정상 시각이 일반 정상 상태와 명확히 구분된다.
- [ ] 숨김 삭제, 복구와 변경 이력이 일반 삭제와 혼동되지 않는다.
- [ ] Q&A 작성자, 답변 여부, 상태 변경과 최종 답변 권한이 화면에 일관되게 반영된다.

## 7. 전환과 시각적 만족도

- [ ] 클릭·선택 직후 시각적 피드백이 제공된다.
- [ ] 패널, 팝업과 화면 전환이 사용자의 시선을 자연스럽게 다음 위치로 안내한다.
- [ ] 장식 애니메이션이 콘텐츠 읽기나 조작을 늦추지 않는다.
- [ ] 여러 카드의 순차 애니메이션이 화면 사용 가능 시점을 지연하지 않는다.
- [ ] 반복 애니메이션은 상태 전달 또는 직접 상호작용과 관련이 있으며 시각적 피로를 만들지 않는다.
- [ ] 이동과 크기 변화는 레이아웃 재배치보다 `opacity`와 `transform` 중심으로 구현됐다.
- [ ] 전환 중 눈에 띄는 끊김, 깜박임, 점프 또는 콘텐츠 위치 변화가 없다.
- [ ] 동작 축소 환경에서는 불필요한 애니메이션이 제거되고 기능과 상태 전달은 유지된다.

## 8. 성능과 안정성

- [ ] 주요 화면은 기존 요구사항인 3초 이내에 표시된다.
- [ ] 주요 전환 중 50ms를 넘는 긴 작업과 프레임 저하 여부를 측정해 기록했다.
- [ ] 입력, 검색, 필터와 팝업 동작에서 반복 클릭이 필요할 정도의 지연이 없다.
- [ ] 애니메이션 중 스크롤, 입력과 버튼 조작이 정상적으로 동작한다.
- [ ] 화면을 반복 이동해도 동작이 중첩되거나 점차 느려지지 않는다.
- [ ] 브라우저 콘솔 오류와 처리되지 않은 예외가 없다.

50ms를 넘는 긴 작업은 자동 실패로 단정하지 않고 발생 위치, 사용자 영향과 반복 여부를 근거로 우선순위를 정한다. 약 50명 동시 사용 성능과 운영 네트워크 성능은 별도 단계에서 검증한다.

## 9. 접근성과 이해 가능성

- [ ] 모든 조작 요소를 키보드로 접근하고 실행할 수 있다.
- [ ] 현재 초점이 모든 화면과 팝업에서 분명히 보인다.
- [ ] 팝업을 닫은 뒤 초점이 적절한 시작 요소로 돌아간다.
- [ ] 본문, 보조 문구, 상태와 비활성 요소의 명도 대비가 충분하다.
- [ ] 상태를 색상만으로 구분하지 않고 아이콘 또는 문구를 함께 제공한다.
- [ ] 제목 구조, 랜드마크, 레이블과 상태 알림이 보조 기술에 전달된다.
- [ ] 오류 원인과 다음 행동을 쉬운 문장으로 안내한다.
- [ ] 자동 접근성 검사 결과와 수동 키보드 검토 결과를 구분해 기록한다.

## 10. 결과 정리

- [ ] 발견 사항을 `확인`, `미검증`, `의견`으로 구분했다.
- [ ] 각 발견 사항에 `P0`, `P1`, `P2` 우선순위를 부여했다.
- [ ] 스크린샷 또는 측정값이 대상 화면·상태·화면 크기와 연결돼 있다.
- [ ] 공식 근거 스크린샷과 측정 산출물이 임시 경로가 아닌 `docs/design-reviews/assets/` 아래에 보존돼 있다.
- [ ] 디자인 개선이 기존 요구사항과 사용 흐름에 미치는 영향을 기록했다.
- [ ] 미검증 항목에 사유와 다음 확인 시점을 기록했다.
- [ ] 사용자 피드백으로 드러난 누락·오판·방향 불일치를 일회성 내용과 재사용 기준으로 구분하고, 새 기준은 다음 검토 확인 항목으로 남겼다.
- [ ] 메인 개발자가 재현·재검증할 수 있는 정보가 포함됐다.
- [ ] 독립 검토 판정과 메인 개발자 재검증 판정을 분리해 기록했고, 메인 개발자 확인으로 `보류`를 상향하지 않았다.
- [ ] 보고서 대상 상태와 현재 변경 상태가 일치하며 보고서가 `유효`한지 마지막으로 확인했다.
- [ ] 최종 판정을 `통과`, `조건부 통과`, `보류` 중 하나로 기록했다.
