# Quality Hub 개발 계획

**현재 상태:** 1단계 UI/UX 설계 완료 · 2단계 UI 프로토타입 구현 완료 · 3단계 로컬 기능 구현 부분 완료 · 독립 디자인 필수 2항목 재검토 필요

이 문서는 현재 단계와 판정의 단일 기준이다. README와 요구사항은 현재 상태를 중복 서술하지 않고 이 문서를 참조하며, 완료 보고서와 디자인 검토 보고서는 실행 당시의 증거 스냅샷으로 보존한다.

## 1단계: UI/UX 설계 · 완료

- 전체 메뉴와 화면 이동 구조 정의
- Supabase 디자인을 참고한 공통 디자인 규칙 작성
- 대시보드, Report 조회, 품질 Agent, 검색, Rule, Q&A 및 관리자 화면 설계
- 데이터 원천 관리 화면은 제외하고 별도 DB 관리 경계 명시
- PC 데스크톱 화면과 접근성 기준 반영(모바일·태블릿 제외)

**완료 기준:** 전체 화면 구성과 주요 사용자 흐름을 확인할 수 있다.

현재 목업에서 전체 메뉴, 주요 화면 구성과 이동 흐름을 확인했고 사용자가 현재 안을 승인했다. 실제 연동·저장·권한 집행과 운영 품질 검증은 1단계 완료 근거에 포함하지 않는다.

## 2단계: UI 프로토타입 구현 · 완료

**착수 근거:** [디자인 전문 검토 에이전트](DESIGN_REVIEW_AGENT.md)가 승인 목업을 읽기 전용으로 검토하고 메인 개발자가 결과를 재검증했다.

2026-08-06 기준선 검토는 P0 없이 `조건부 통과`했다. 명도 대비·초점 관리·Agent 랜드마크를 반영하고 성능을 다시 측정했다. 세부 근거는 [기준선 디자인 검토 보고서](archive/design-reviews/2026-08-06-2단계-시작-전-디자인-검토.md)와 [2단계 완료 보고서](PHASE2_COMPLETION_REPORT.md)를 따른다.

- 현재 목업을 기준으로 빠진 상호작용과 화면 상태를 보완
- 마스터·관리자·일반유저 역할을 임시로 전환하고 역할별 노출·조작 범위를 확인하는 기능 제공
- 로딩, 데이터 없음, 조회 오류·재시도, 오래된 데이터와 권한 없음 상태 표현
- 복구 가능한 숨김 삭제, 복구와 변경 이력 조회 흐름을 목업 데이터로 구현
- Q&A 작성자·답변 존재 여부·상태 변경·최종 답변 지정 권한 흐름 구현
- 화면에 직접 고정된 예시 데이터를 교체 가능한 모의 데이터 계층으로 분리
- 미확정 품질 지표를 교체 가능한 예시 지표로 유지

**완료 기준:** 실제 데이터 없이 주요 기능을 별도 설명 없이 찾고 전체 사용 흐름을 체험할 수 있으며, 디자인 전문 최종 검토와 메인 개발자 재검증을 통과한다.

2026-08-06 역할·공통 상태·숨김·복구·이력과 Q&A 권한 흐름을 구현했다. 중간 검토 P1을 반영하고 완료 전 디자인 검토와 메인 개발자 재검증을 통과했다. 근거와 운영 제외 범위는 [2단계 완료 보고서](PHASE2_COMPLETION_REPORT.md)에 기록한다.

## 3단계: 로컬 기능 구현 · 부분 완료

- Rule&SOP 등록·수정 및 개정 이력 관리
- Q&A 작성·답변·상태 관리
- 포털 내부 알림과 통합 검색
- 향후 실제 데이터 연결을 위한 공통 연동 규격 구현

**완료 기준:** 테스트 데이터로 주요 기능과 역할별 권한 흐름이 정상 동작한다.

2026-08-08 실제 사내 데이터 대신 가상 데이터를 사용해 Rule&SOP 문서·개정 이력, Q&A·알림·변경 이력을 브라우저 로컬 저장 계층에 연결했다. 통합 검색은 현재 Report, Rule&SOP와 Q&A 데이터를 동적으로 반영한다. 후속 작업에서 Q&A 지연 로딩과 Report 검색 도착 초점을 보정했고, 독립 검토에서 검색 세 목적지와 Q&A 알림 흐름을 확인했다. 125% 확대 검증은 사용자 결정으로 `해당 없음`이며, 콘솔·전체 키보드 흐름이 미검증으로 남아 전체 단계는 `부분 완료`다. 해당 항목을 독립 재검토한 뒤 완료 여부를 다시 판정한다. 실제 DB·Parquet 스키마 호환성은 최종 사내 데이터 연결 시점인 4단계에서 검증·조정한다. 상세 근거와 제한사항은 [3단계 진행 보고서](PHASE3_COMPLETION_REPORT.md)와 [완료 전 디자인 검토 보고서](design-reviews/2026-08-08-3단계-완료-전-디자인-검토.md)에 기록한다.

## 4단계: 실제 사내 시스템 연동

- Parquet, 사내 DB, 공유 폴더 및 문서 URL 연동
- 사내 SSO 연결과 유저 ID·소속부서 기반 접근 권한 판정
- 핵심 품질 지표와 계산식 반영
- 최종 사내 데이터의 실제 스키마를 기준으로 3단계 로컬 데이터 계약의 필드·자료형·키 호환성 검증 및 조정

**승인 필요:** 외부 시스템 실제 연결 전 사용자 승인을 받는다.

**완료 기준:** 최신 데이터 반영, 장애 시 마지막 정상 데이터 표시, 권한 제한을 검증한다.

## 5단계: 검증 및 공개 준비

- 자동·회귀 테스트와 코드 검토
- 약 50명 사용 기준 주요 화면 3초 이내 성능 검증
- 보안·접근성 검토와 운영·복구 문서 작성
- 배포 환경 확정 및 배포 계획 수립

**완료 기준:** 모든 검증을 통과하고 남은 위험이 문서화되어 공개 승인 요청이 가능하다.

## 검증 명령과 확대 기준

현재 Vite 기반 목업과 자동 테스트가 있으므로 변경 유형에 맞는 가장 작은 검증부터 시작한다. `npm test` 전체 실행과 `npm run build`는 모든 작업의 기본 절차가 아니라 공통 계약 변경, 단계 완료와 공개 준비 검증에 사용한다. 세부 변경 유형별 기준은 [메인 개발자 역할 정의](MAIN_DEVELOPER_ROLE.md)의 `변경 유형별 기본 검증`을 따른다.

- 문서·단일 계약: 관련 `tests/*.test.mjs`만 `node --test`로 실행하고 `git diff --check` 확인
- React 컴포넌트: 관련 Vitest 파일과 필요한 브라우저 상태만 확인
- 서버·HTTP 계약: `tests/server.test.mjs`를 별도 실행하며 localhost 권한 오류를 제품 실패와 구분
- 공통 CSS·컴포넌트·내비게이션·빌드 설정: 영향받는 테스트 묶음과 `npm run build` 실행
- 단계 완료·공개 준비: `npm test`, 프로덕션 빌드와 해당 단계의 전체 검증 실행
- 의존성 파일 변경 또는 단계·공개 검증이 아니면 `npm audit`을 반복하지 않음

단계가 바뀔 때마다 필요한 검증 구조를 아래 기준으로 다시 검토한다.

- 3단계 시작 전: 모의 데이터 계약, 자동 테스트 및 변경 검증 게이트
- 4단계 시작 전: 실제 연동과 분리된 QA·보안·성능 검증 구조

각 검토에서는 해당 단계에 필요한 최소 구조만 도입한다.

## 선행 확인 사항

- 핵심 지표와 계산식
- 원천별 스키마·경로·접속 권한
- SSO 규격과 문서 형식
- 최종 배포 환경 및 사내 보안 기준

## 개발 원칙

- 기능과 디자인은 품질 정보 탐색과 담당자 소통의 불편을 줄이는 방향을 우선한다.
- 테스트 데이터는 실제 데이터가 아님을 화면과 문서에 명확히 표시한다.
- UI에 테스트 데이터를 직접 고정하지 않고 모의 데이터 연결 계층을 통해 제공한다.
- 실제 연동 시 UI를 다시 만들지 않도록 모의 데이터와 실제 데이터가 같은 규격을 사용한다.
