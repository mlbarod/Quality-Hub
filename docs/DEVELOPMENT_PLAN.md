# Quality Hub 개발 계획

**현재 상태:** 1단계 UI/UX 설계 완료 · 2단계 UI 프로토타입 구현 완료 · 3단계 로컬 기능 구현 부분 완료 · 4단계 진행 중 · 독립 디자인 필수 2항목 재검토 필요

**1차 시범 운영 전환:** Docker Compose 운영 구조와 로컬 컨테이너 검증 완료 · 실제 운영 서버 배포 미완료

이 문서는 현재 단계와 판정의 단일 기준이다. README와 요구사항은 현재 상태를 중복 서술하지 않고 이 문서를 참조하며, 완료 보고서와 디자인 검토 보고서는 실행 당시의 증거 스냅샷으로 보존한다.

## 1차 시범 운영 원칙

2026-08-11 사용자 결정에 따라 현재 모든 기능을 열어 둔 채 운영을 시작하고 미완료 단계는 운영 중 순차 진행한다. 2026-08-14 Rule&SOP는 `rulesop` 실제 DB 조회로 전환했고 Q&A와 알림은 현재 브라우저 로컬 저장 방식을 유지한다. SSO 비활성화 배포는 기존 사내 리버스 프록시의 사내망·허용 IP 제한만 사용하므로 역할 미리보기가 실제 권한이 아니다.

운영용 다단계 이미지, Docker Compose, 빌드 기본 실행, health·readiness, 보안 헤더, 정상 종료와 운영·복구 절차를 구성하고 로컬 컨테이너에서 확인했다. 제공된 운영 서버 호스트명이 현재 개발 환경에서 DNS 해석되지 않아 실제 서버 배포·리버스 프록시 연결·사내 연동 확인은 아직 `미완료`다. 이 시범 운영 전환은 3·4·5단계 완료 판정을 상향하지 않는다.

**완료 기준:** 전체 화면 구성과 주요 사용자 흐름을 확인할 수 있다.

현재 목업에서 전체 메뉴, 주요 화면 구성과 이동 흐름을 확인했고 사용자가 현재 안을 승인했다. 실제 연동·저장·권한 집행과 운영 품질 검증은 1단계 완료 근거에 포함하지 않는다.

2026-08-06 기준선 검토는 P0 없이 `조건부 통과`했다. 명도 대비·초점 관리·Agent 랜드마크를 반영하고 성능을 다시 측정했다. 세부 근거는 [기준선 디자인 검토 보고서](archive/design-reviews/2026-08-06-2단계-시작-전-디자인-검토.md)와 [2단계 완료 보고서](PHASE2_COMPLETION_REPORT.md)를 따른다.

- 복구 가능한 숨김 삭제, 복구와 변경 이력 조회 흐름을 목업 데이터로 구현

**완료 기준:** 실제 데이터 없이 주요 기능을 별도 설명 없이 찾고 전체 사용 흐름을 체험할 수 있으며, 디자인 전문 최종 검토와 메인 개발자 재검증을 통과한다.

2026-08-06 역할·공통 상태·숨김·복구·이력과 Q&A 권한 흐름을 구현했다. 중간 검토 P1을 반영하고 완료 전 디자인 검토와 메인 개발자 재검증을 통과했다. 근거와 운영 제외 범위는 [2단계 완료 보고서](PHASE2_COMPLETION_REPORT.md)에 기록한다.

## 3단계: 로컬 기능 구현 · 부분 완료

- Rule&SOP 등록·수정 및 개정 이력 관리
- Q&A 작성·답변·상태 관리
- 포털 내부 알림과 통합 검색
- 향후 실제 데이터 연결을 위한 공통 연동 규격 구현

**완료 기준:** 테스트 데이터로 주요 기능과 역할별 권한 흐름이 정상 동작한다.

2026-08-08 실제 사내 데이터 대신 가상 데이터를 사용해 Rule&SOP 문서·개정 이력, Q&A·알림·변경 이력을 브라우저 로컬 저장 계층에 연결했다. 통합 검색은 현재 Report, Rule&SOP와 Q&A 데이터를 동적으로 반영한다. 후속 작업에서 Q&A 지연 로딩과 Report 검색 도착 초점을 보정했고, 독립 검토에서 검색 세 목적지와 Q&A 알림 흐름을 확인했다. 125% 확대 검증은 사용자 결정으로 `해당 없음`이며, 콘솔·전체 키보드 흐름이 미검증으로 남아 전체 단계는 `부분 완료`다. 해당 항목을 독립 재검토한 뒤 완료 여부를 다시 판정한다. 실제 DB·Parquet 스키마 호환성은 최종 사내 데이터 연결 시점인 4단계에서 검증·조정한다. 상세 근거와 제한사항은 [3단계 진행 보고서](PHASE3_COMPLETION_REPORT.md)와 [완료 전 디자인 검토 보고서](design-reviews/2026-08-08-3단계-완료-전-디자인-검토.md)에 기록한다.

## 4단계: 실제 사내 시스템 연동

- Parquet, 사내 DB, 공유 폴더 및 문서 URL 연동
- 사내 SSO 연결과 유저 ID·소속부서 기반 접근 권한 판정
- 핵심 품질 지표와 계산식 반영
- 최종 사내 데이터의 실제 스키마를 기준으로 3단계 로컬 데이터 계약의 필드·자료형·키 호환성 검증 및 조정

**승인 필요:** 외부 시스템 실제 연결 전 사용자 승인을 받는다.

**완료 기준:** 최신 데이터 반영, 장애 시 마지막 정상 데이터 표시, 권한 제한을 검증한다.

2026-08-11 품질 Agent의 사내 RAG 검색, GPT-OSS 답변 생성과 MariaDB/MySQL 대화 History를 하나의 Backend 흐름으로 연결하고 기존 우측 패널·전체 화면에서 같은 대화를 사용하도록 구현했다. 실제 SSO 대신 역할 미리보기 user ID를 테스트 식별값으로 사용하며, Streaming·Spotfire·나머지 사내 데이터 연동과 운영 검증은 남아 있으므로 4단계 전체 완료로 판정하지 않는다.

2026-08-11 각종 Report 조회 App의 목록·신규 등록·수정·실제 삭제를 품질 Agent와 같은 DB 환경변수의 `report_reg`에 연결하고, `report_url`을 Spotfire 원본 iframe과 새 창 열기에 사용하도록 구현했다. `user_id`와 `reg_time`은 신규 등록 시 화면에 표시하지 않고 기록한다. 테이블에 고유키가 없어 서버가 목록 조회마다 임시 식별자를 발급하고 수정·삭제 시 원래 6개 컬럼을 모두 대조해 한 행만 처리하며, Report 카드는 여러 시각화 유형을 무작위 순서로 배정한다. 실제 SSO와 Spotfire iframe·인증 정책 및 운영 환경 검증은 남아 있으므로 4단계는 계속 진행 중이다.

2026-08-19 품질 대시보드의 예시 지표 화면을 실제 DB 조회 구조로 교체했다. Report·Rule&SOP와 같은 DB 환경변수로 `dashboard_report.url` 한 건을 조회하고, URL을 별도 가공하지 않은 Spotfire 원본 iframe과 새 창 열기에 사용한다. 로딩·빈 값·DB/URL 오류와 재시도 상태를 제공하며, Spotfire 표시 최대 폭은 Report 뷰어 1710px보다 약 10% 넓은 1881px로 설정했다. 실제 운영 DB URL 존재 여부와 Spotfire SSO·iframe 허용 정책은 운영 환경에서 별도 검증해야 하므로 4단계는 계속 진행 중이다.

2026-08-14 Rule&SOP App의 목록과 대·중·소분류 필터를 품질 Agent와 같은 DB 환경변수의 `rulesop`에 연결했다. `main_category`, `sub_category`, `item`, `title`, `url`을 화면에 매핑하고 카드 선택 시 분류와 원문 링크를 팝업으로 제공하며, 마스터와 관리자는 팝업에서 다섯 표시 컬럼을 수정하거나 해당 행을 실제 삭제할 수 있다. 테이블에 고유키가 없어 서버가 목록 조회마다 사용자별 임시 식별자를 발급하고 수정·삭제 시 원래 7개 컬럼을 모두 NULL-safe 대조해 한 행만 처리한다. 기존 MOCK 표시와 숨김 버튼은 제거했고 개정 이력과 수정 시 개정 내용 코멘트는 제공하지 않는다. 실제 운영 DB 조회·수정·삭제 결과와 원문 URL 접근 정책 검증 전까지 4단계는 계속 진행 중이다.

2026-08-18 변승위 Category는 Excel 표 서식 복사 방식을 폐기하고, PC에서 복사한 10MB 이하 PNG·JPEG·WebP 그림 한 장을 붙여넣어 미리보기 후 교체하는 방식으로 변경했다. 조회 방식이 Category 박스 내부 표시에서 별도 팝업으로 변경됨에 따라 1280×600 강제 변환을 제거하고 파일 형식과 원본 해상도를 그대로 저장한다. 조회 팝업은 원본 크기와 비율을 우선하며 화면 폭을 넘을 때만 축소한다. App에서 교체한 최신 그림을 여러 사용자·서버 인스턴스가 공유하고 읽기 전용 컨테이너 재배포 후에도 유지해야 하므로 같은 DB의 별도 `quality_hub_change_category` 테이블에 `singleton_id = 1`인 이미지 BLOB 한 건으로 저장한다. 마스터·관리자만 교체하고 모든 사용자는 조회할 수 있다. 테이블 DDL은 자동 실행하지 않는 수동 마이그레이션으로 제공하며 실제 운영 DB 적용과 SSO 역할별 통합 검증 전까지 이 연동은 `부분 완료`이고 4단계는 계속 진행 중이다.

이전 Excel 하이브리드 초안 DDL을 이미 적용한 환경은 신규 DDL을 덮어쓰지 않고 `002_change_category_excel_to_image.sql`을 사용해 기존 테이블을 `quality_hub_change_category_excel_backup`으로 보존한 뒤 이미지 테이블을 생성한다. 신규 환경은 `002_change_category.sql`만 적용한다.

2026-08-14 AD FS OpenID Connect `form_post` 인증, RS256 JWT 검증, DB 세션, 마스터·접근 규칙 저장과 서버 API 권한 경계를 구현했다. 실제 issuer와 Claim 키가 가이드에 없어 값 없이 키·자료형만 기록하는 1회성 확인 모드를 제공하며, `SSO_ENABLED=false`와 SSO Compose 오버레이 제거로 기존 동작을 복구할 수 있다. 이 환경에서는 사내 IdP와 운영 DB에 접근할 수 없으므로 실제 로그인·Claim 매핑·프록시 쿠키·DB 마이그레이션은 `미검증`이며 4단계는 계속 진행 중이다.

## 5단계: 검증 및 공개 준비

- 자동·회귀 테스트와 코드 검토
- 약 50명 사용 기준 주요 화면 3초 이내 성능 검증
- 보안·접근성 검토와 운영·복구 문서 작성
- 배포 환경 확정 및 배포 계획 수립

**완료 기준:** 모든 검증을 통과하고 남은 위험이 문서화되어 공개 승인 요청이 가능하다.

1차 시범 운영용 Docker Compose와 운영 절차, SSO 코드·롤백 구조는 준비했지만 실제 운영 서버 배포, 사내 SSO·권한 검증, 약 50명 성능, 보안·접근성 전체 검증과 복구 훈련은 남아 있으므로 5단계는 완료되지 않았다.

## 검증 명령과 확대 기준

현재 Vite 기반 목업과 자동 테스트가 있으므로 변경 유형에 맞는 가장 작은 검증부터 시작한다. `npm test` 전체 실행과 `npm run build`는 모든 작업의 기본 절차가 아니라 공통 계약 변경, 단계 완료와 공개 준비 검증에 사용한다. 세부 변경 유형별 기준은 [메인 개발자 역할 정의](MAIN_DEVELOPER_ROLE.md)의 `변경 유형별 기본 검증`을 따른다.

- 문서·단일 계약: 관련 `tests/*.test.mjs`만 `node --test`로 실행하고 `git diff --check` 확인
- React 컴포넌트: 관련 Vitest 파일과 필요한 브라우저 상태만 확인
- 서버·HTTP 계약: `tests/server.test.mjs`를 별도 실행하며 localhost 권한 오류를 제품 실패와 구분
- 공통 CSS·컴포넌트·내비게이션·빌드 설정: 영향받는 테스트 묶음과 `npm run build` 실행
- 단계 완료·공개 준비: `npm test`, 프로덕션 빌드와 해당 단계의 전체 검증 실행
- 의존성 파일 변경 또는 단계·공개 검증이 아니면 `npm audit`을 반복하지 않음

단계가 바뀔 때마다 필요한 검증 구조를 아래 기준으로 다시 검토한다.

- 3단계 시작 전: 모의 데이터 계약, 자동 테스트 및 변경 검증 게이트
- 4단계 시작 전: 실제 연동과 분리된 QA·보안·성능 검증 구조

각 검토에서는 해당 단계에 필요한 최소 구조만 도입한다.

## 선행 확인 사항

- 핵심 지표와 계산식
- 원천별 스키마·경로·접속 권한
- SSO 규격과 문서 형식
- 최종 배포 환경 및 사내 보안 기준

## 개발 원칙

- 기능과 디자인은 품질 정보 탐색과 담당자 소통의 불편을 줄이는 방향을 우선한다.
- 테스트 데이터는 실제 데이터가 아님을 화면과 문서에 명확히 표시한다.
- UI에 테스트 데이터를 직접 고정하지 않고 모의 데이터 연결 계층을 통해 제공한다.
- 실제 연동 시 UI를 다시 만들지 않도록 모의 데이터와 실제 데이터가 같은 규격을 사용한다.
